Easy explanation

Testing helps check software quality and reliability and protect users from defects. The consequences of failures can be serious, so testing is an important part of development.

Example: Testing a medical appointment system can help catch an error before it disrupts a patient’s booking.

Key terms to remember
  • Testing imperative: Protecting software quality, reliability, and user satisfaction while reducing the risk of costly or dangerous failures.

Easy explanation

An error is a human mistake; it can introduce a defect, or bug, in software. A failure is the incorrect behavior users or systems observe when that defect runs.

Example: A developer mistypes a formula (error), the wrong formula is in the code (defect), and a total is incorrect (failure).

Key terms to remember
  • Error: A human mistake, such as misunderstanding requirements or typing an incorrect formula.
  • Defect / bug: A flaw in software resulting from a human error.
  • Failure: An observable incorrect behavior when a defect manifests during execution.

Easy explanation

A test case describes how to check something: its setup, actions, expected outcome, observed outcome, and pass/fail result.

Example: For login, specify a valid account, enter credentials, and expect the account page to appear.

Key terms to remember
  • Test case: An identified test with a description, setup, steps, expected result, actual result, and pass/fail outcome.
Slide 6 of 18 · Open in PDF
Easy explanation

A test plan describes the overall testing strategy, including scope, goals, resources, schedule, and criteria. A test suite groups related test cases.

Example: A login suite can collect tests for valid, invalid, and locked-account sign-ins.

Key terms to remember
  • Test plan: A project-wide testing strategy defining scope, objectives, resources, schedule, and entry/exit criteria.
  • Test suite: A logical collection of related test cases organized for particular testing objectives.

Easy explanation

Quality Assurance (QA) focuses on preventing defects through processes across development. Quality Control (QC) checks the product to find defects and verify requirements.

Example: A code review is QA; running system tests to find a problem is QC.

Key terms to remember
  • Quality assurance / QA: Proactive, process-focused defect prevention throughout the SDLC through standards and activities such as reviews.
  • Quality control / QC: Product-focused identification of defects and verification that outputs meet requirements, including system testing and UAT.

Easy explanation

White-box testing uses knowledge of the code’s internal structure. Testers can target logic paths and measure which code tests execute.

Example: A unit test can exercise both the true and false branches of a condition.

Key terms to remember
  • White-box testing: Testing with full knowledge of internal code and structure, focusing on paths, loops, and coverage.
  • Code coverage: A measure of which code has been executed by tests, used in the lesson's white-box testing discussion.
Slide 9 of 18 · Open in PDF
Easy explanation

Black-box testing checks behavior from the outside without relying on knowledge of internal code. It compares inputs and outputs with requirements.

Example: Enter an incorrect password and verify that sign-in is rejected.

Key terms to remember
  • Black-box testing: Evaluating inputs, outputs, and behavior against requirements without access to internal code.
Slide 10 of 18 · Open in PDF
Easy explanation

Gray-box testing combines external behavior checks with partial knowledge of internals, such as a database schema, to design more focused tests.

Example: Knowing how account data is stored can help test whether a profile update reaches the right record.

Key terms to remember
  • Gray-box testing: A hybrid approach using partial internal knowledge, such as database schemas, to guide tests.

Easy explanation

Unit testing checks one small component in isolation, often early in functional testing. It helps confirm that each piece works as designed.

Example: Test a discount-calculation function with a known price and discount.

Key terms to remember
  • Unit testing: Testing individual components in isolation, typically by developers using frameworks such as JUnit or NUnit.

Easy explanation

Integration testing checks whether connected units exchange information and work together correctly.

Example: Verify that the authentication module reads the correct user record from the database.

Key terms to remember
  • Integration testing: Verifying interfaces and interactions between combined units, such as authentication and database modules.

Easy explanation

System testing checks the complete integrated application against requirements, often in an environment similar to production.

Example: Run an end-to-end banking transaction through sign-in, transfer, and confirmation.

Key terms to remember
  • System testing: Testing the entire integrated system against requirements in a production-like environment.
Slide 14 of 18 · Open in PDF
Easy explanation

Acceptance testing, often called UAT, lets end users check whether the system meets business needs and is ready to use.

Example: A client validates that a CRM supports the tasks their staff need before sign-off.

Key terms to remember
  • Acceptance testing / UAT: End-users validating fitness for business use and readiness for deployment.
Slide 15 of 18 · Open in PDF
Easy explanation

Non-functional testing evaluates qualities of operation rather than a particular feature, including speed, security, usability, reliability, and maintainability.

Example: Performance testing checks whether a site remains responsive under heavy use.

Key terms to remember
  • Non-functional testing: Evaluating operational qualities such as performance, security, usability, reliability, and maintainability.
  • Performance testing: Assessing operational characteristics such as speed and scalability.
  • Security testing: Evaluating vulnerabilities as an operational quality of software.
  • Usability testing: Evaluating ease of use as a non-functional quality.
Slide 16 of 18 · Open in PDF
Easy explanation

A well-formed test case states what must be true first, the steps to take, and the expected result to compare with what happens.

Example: For password reset, start with an existing account, request an email link, set a new password, and verify login.

Key terms to remember
  • Test preconditions: Setup requirements that must hold before executing a test, such as an existing user with a valid email.
  • Expected result: The predicted correct outcome used to judge actual behavior, such as a successful password update and subsequent login.
