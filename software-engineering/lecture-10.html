Slide 3 of 14 · Open in PDF
Easy explanation

GitHub hosts projects and supports people collaborating around Git repositories. It is used for both open-source and professional software work.

Example: Several contributors can discuss and improve a shared project even when they work in different places.

Key terms to remember
  • GitHub: A collaborative software-development platform that hosts Git repositories and supports community participation and review.
Slide 4 of 14 · Open in PDF
Easy explanation

A version control system records file changes over time. Git is distributed, and GitHub hosts Git repositories so teams can collaborate and recover earlier versions.

Example: If a recent edit causes a problem, the history can help identify or restore a stable version.

Key terms to remember
  • Version control system: A system tracking and managing file changes over time with revision history, collaboration, and recovery.
  • Git: The distributed version-control system underlying the repositories hosted by GitHub.
Slide 5 of 14 · Open in PDF
Easy explanation

Version control provides change history, supports concurrent work, makes experimentation safer through branches, and allows recovery to an earlier state.

Example: Try a new feature on a branch while keeping the main code line available.

Key terms to remember
  • Revision history and rollback: Recorded modifications that allow teams to inspect changes and restore a previous stable state.
Slide 6 of 14 · Open in PDF
Easy explanation

With Git’s distributed model, each developer has a full local repository copy. They can work offline and later share changes through GitHub.

Example: A developer commits changes locally during travel and pushes them after reconnecting.

Key terms to remember
  • Distributed repository copy: A full local repository copy supporting offline work and resilient recovery in Git's distributed model.
Slide 7 of 14 · Open in PDF
Easy explanation

A branch is an independent line of development. It lets someone work on a feature or fix while leaving the main branch undisturbed.

Example: Create feature/search to build search without changing main until it is ready.

Key terms to remember
  • Branching: Creating independent development lines to isolate features or fixes from the stable main branch.
Slide 8 of 14 · Open in PDF
Easy explanation

The workflow is to create a feature branch, make and commit changes locally, then push that branch to GitHub. The work remains separate until reviewed and merged.

Example: Commit small search-feature changes to feature/search, then push the branch.

Key terms to remember
  • Create feature branch: The workflow step that starts a separate line from main, such as feature/auth.
  • Develop and commit locally: Making changes and recording them as commits on the feature branch before pushing to the remote.
  • Push to remote: Sending local branch commits to a remote repository while keeping feature work separate from main until integration.
Slide 9 of 14 · Open in PDF
Easy explanation

A pull request proposes merging a branch into another branch. It provides a place for code review and discussion before the changes join the main code line.

Example: Open a PR from feature/search to main so teammates can review it.

Key terms to remember
  • Pull request: A proposal to merge changes into a target branch, initiating review and discussion before integration.
Slide 10 of 14 · Open in PDF
Easy explanation

To open a PR, push the branch, start a pull request on GitHub, choose the base and compare branches, add a clear title and description, and submit it for review.

Example: Set main as the base and feature/search as the compare branch, then summarize what changed.

Key terms to remember
  • Base and compare branches: The pull-request selections identifying the target branch and the branch containing proposed changes.
  • PR title and description: Clear explanatory details that communicate the purpose and content of proposed changes to reviewers.
Slide 11 of 14 · Open in PDF
Easy explanation

Reviewers give constructive feedback; automated checks can run tests; conflicts need resolution before approved work is merged. Merging integrates the changes into the target branch.

Example: Fix a failing check and resolve overlapping edits before completing the PR.

Key terms to remember
  • Constructive code review: Collaborators examining proposed changes and offering improvements before integration.
  • Automated PR checks: CI/CD tests run on proposed work to help validate changes before merging.
  • Merge conflict resolution: Reconciling incompatible changes as part of preparing proposed work for approval and integration.
  • Merging: Integrating approved changes from a feature branch into the target branch.
